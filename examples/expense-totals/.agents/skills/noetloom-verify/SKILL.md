---
name: noetloom-verify
description: Verify real behavior, repair gaps, and finish an autonomous project's agreed boundary with current evidence.
---

Read the objective, accepted changes, selected phase's acceptance, relevant guidance,
and validation owner. Choose checks that would fail for a plausible broken implementation.
Run focused checks during implementation and broader checks when shared contracts or
new concerns justify them. Exercise the actual CLI, API, or UI and inspect results.
Generated files, markers, or framework consistency alone do not prove application behavior.

Diagnose and repair failures; add meaningful regression coverage where warranted.
Review acceptance coverage, integration, error handling, documentation, maintainability,
and residual risks. If requested behavior is missing from the plan, revise the plan and
implement necessary work within existing authority. An empty queue is not completion.

Keep concise local evidence: commands/scenarios, results, source revision or input
identity, and actual limitations. Tie completion to current acceptance and source.
Preserve historical results, but revalidate affected outcomes after relevant changes.
Mark the phase complete only when its outcome is demonstrated, then continue ready work.

At the agreed completion boundary, exercise a representative full journey, compare the
application against the objective and all accepted steering, and review continuation
instructions as a fresh reader. Follow authorized Git/CI delivery through checks and
repair. Stop at the actual external permission boundary; do not invent deployment,
publication, spending, or communication authority.

Report the implemented result, meaningful checks, remaining limitations, and any external
boundary. Record a response as delivered only after delivering it. Leave local continuation
state when work remains. Distinguish actual host execution from compatibility inspection.

If the project opted into helper-managed evidence, read its local helper reference:
declare complete input patterns, run its verify checks, regenerate edited adapters, and
complete with current passing records. The helper cannot judge test adequacy or behavior;
ordinary application verification and the readable method remain authoritative.
